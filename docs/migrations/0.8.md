# Migrating to Karni 0.8.0

## Changed in 0.8.0

### Karni and its modules are held at one version line

`karni new` writes `karni` and each Karni module with the range of the
release that made the project (`karni>=0.8,<0.9`), and `karni add <module>`
adds a module at the range `karni` has. A project made with 0.7.0 lists them
bare, so an install takes the newest of each that day, and installing a
module's extra can move `karni` to another line. Nothing breaks when you
upgrade. The warning [`karni.W521`](../errors.md#w521-karni-karni-cli-and-the-modules-are-not-on-one-version-line) now says at start-up
when `karni`, `karni-cli` and the installed modules are not on one line.

**What to do.** Run `karni upgrade`: it writes the range for every Karni name
that `pyproject.toml` lists bare, and `--dry-run` shows what it would write.
Or write the ranges yourself, then install again:

```toml
[project]
dependencies = [
    "karni>=0.8,<0.9",
    "karni-site[images]>=0.8,<0.9",
]
```

[Stability](../stability.md#holding-a-project-on-a-version-line) says how a
project moves to a newer line.

### The side menu of a site project

0.8.0 adds `KARNI_ADMIN_MENU`, the admin's side menu in groups, and
karni-site's `KARNI_SITE_ADMIN_MENU`: the project's own apps, the site's
pages, then users and roles. The technical apps (task results, schedules,
tokens, sign-in codes) show to superusers only. The admin's home page and the
guide's *What each section is for* show the same groups. A site project made
with 0.8.0 sets it. A site project made with 0.7.0 keeps the list of every
app, as before.

**What to do.** To give a client the grouped menu, add this line to
`config/settings.py`, after the call to `karni_settings()`:

```python
KARNI_ADMIN_MENU = KARNI_SITE_ADMIN_MENU  # noqa: F821
```

Hiding an entry changes no permission: a page the menu leaves out still opens
from its address for whoever may open it. Groups of your own are in
[the side menu](../admin.md#the-side-menu).

### Karni's makemigrations and migrate

Karni now has its own `makemigrations` and `migrate` commands, in place of
Django's. They differ in one thing: when the definition of a generated field
changes (the `sources` of a `SearchField`), they write `RemoveField` and
`AddField`, with the field's indexes, constraints and `unique_together`
entries set aside and put back, where Django wrote an `AlterField` that
`migrate` refused to run. Every other change is written as before, and
migrations already written are not touched. The two commands are
[experimental](../stability.md#experimental-names).

**What to do.** Nothing for most projects. A project that has a migration
from 0.7.0 with an `AlterField` on a generated field, which `migrate` stopped
on, deletes that migration and runs `karni make migration` again. To keep
Django's commands, see
[changing a generated field](../fields.md#changing-a-generated-field).

### An admin registered by hand takes AdminMeta

In 0.7.0 only the admin Karni derives read a model's `AdminMeta` and the
inlines other models declare with `inline_on`. Now a `KarniModelAdmin`
subclass registered by hand takes them too, for each option it does not set
itself. An admin registered by hand for a model with an `AdminMeta` can show
other columns, filters, a page size or inlines after the upgrade.

**What to do.** Open the admin pages you registered by hand. To keep one as
it was, set the option on the subclass, or return `{}` from its
`admin_meta_options(model)` and `[]` from its `derive_inlines(model)`. See
[a subclass registered by hand](../admin.md#a-subclass-registered-by-hand).

### New checks that can stop a project

- [`karni.E971`](../errors.md#e971-languages-names-a-language-django-has-no-lang_info-entry-for): `LANGUAGES` names a code that Django has
  no `LANG_INFO` entry for, while `django.contrib.admin` is installed. With
  0.7.0 the project started, and then every admin change form answered 500.
  Now it stops at start-up with this error, which shows the entry to add.
  **What to do:** register the language in `settings.py` (`from
  django.conf.locale import LANG_INFO`, then `LANG_INFO.update({...})` with
  the entry the message shows), or take the code out of `LANGUAGES`. Without
  the admin it is the warning `karni.W971`.
- [`SITE026`](../errors.md#site026-karni_site_editor_grants-adds-a-grant-the-editor-role-cannot-give) (karni-site): `karni check` fails when
  `KARNI_SITE_EDITOR_GRANTS`, new in 0.8.0, names a grant the editor role
  cannot give, or adds nothing because `KARNI_SITE_EDITOR_ROLE` is `None` or
  `KARNI_ROLES` replaces the role. Only a project that sets the new setting
  meets it. **What to do:** write each grant as the message says, or move
  the grants into the role in `KARNI_ROLES` that replaces karni-site's.
