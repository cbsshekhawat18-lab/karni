# Migrating to Karni 0.4.1

Every change below is recorded in Karni's machine-readable changelog
(`packages/karni/karni/changelog/0.4.1.toml`). Nothing here breaks a 0.4.0
project's build or tests. `karni upgrade` adds the URL marker, reports
anything it could not place, and lists the public-read viewsets to review and
the agent files to regenerate. Changing who may write a resource is the
project's decision, so no codemod touches access. `karni check` may print a
new warning.

## Upgrading

```bash
pipx upgrade karni-cli        # the CLI carries the changelog
karni upgrade --dry-run       # shows the diff and the notes below, writes nothing
karni upgrade                 # applies the codemod on a clean git tree
# then pin karni to 0.4.1 in pyproject.toml, reinstall, and run:
karni rules sync              # rewrite the agent files
karni check                   # prints karni.W102 for each viewset to review
karni check --deploy          # before going live, with production settings
```

## Changed in 0.4.1

### Public-read viewsets: review who may write

This is a security fix. In 0.4.0, `karni make model ... --access public-read`
and `karni make viewset ... --access public-read` wrote this declaration:

```python
access = Access(read=Public(), write=Authenticated())
```

A new project also has open self-registration (`POST /api/auth/register/`).
Together they let anyone who opens an account create, change and delete
every row of the resource through the API. The test `karni make test`
generated acted as any signed-in user, so it passed and did not catch it.
The problem was found in a real project built on 0.4.0.

From 0.4.1, `--access public-read` writes:

```python
access = Access(read=Public(), write=HasRole("staff"))
```

`staff` is the system role in the default `KARNI_ROLES`.
`--access public-read:<role>` names another role, for example
`public-read:editor`. `karni make test` now acts as the role the `write`
predicate names, so the generated test really creates, updates and deletes.

What to do in a 0.4.0 project:

1. Run `karni check`. Each viewset whose `write` lets every signed-in user
   change every row is reported as [karni.W102](../errors.md#w102-any-self-registered-user-may-change-and-delete-every-row-of-a-resource).
2. For each one, decide who may write and change `write`. Use
   `HasRole("staff")` (what the preset writes now), `Granted()` (the roles'
   grants) or `Owned("<field>")` (rows the user owns).
3. If a generated test now fails because its user cannot write, pass the
   role: `self.assert_crud(VenueViewSet, "staff")`, or regenerate it with
   `karni make test Venue --force`.

`create=Authenticated()` with an owned `write` (anyone signed in may add a
row, and only its owner may change it) is the normal pattern for content
users create, and W102 does not report it.

### Self-registration can be turned off

`KARNI_ACCOUNTS_REGISTRATION` (default `True`, so nothing changes) decides
whether anyone may open an account. `False` leaves `register/` out of the
URLs, so it answers 404 and is absent from the OpenAPI schema. Use it when
staff create every account, for example a brochure site with a CMS. W102
is silent while registration is off. See
[closing registration](../accounts.md#closing-registration).

If every signed-in user is trusted to write and W102 is wrong for your
project, add `"karni.W102"` to `SILENCED_SYSTEM_CHECKS`.

### Public creates are rate-limited

A viewset whose `create` anyone may call (`create=Public()`, or
`write=Public()` without a `create`) now gets three protections without a
line of code:

- **A rate limit.** Each caller (the user, else the client IP) may create
  `KARNI_PUBLIC_CREATE_RATE` rows, default 10 an hour. Over it, `create`
  answers 429 with `Retry-After`. A 0.4.0 project that wrote its own
  `get_throttles()` for a contact form keeps it: an overridden
  `get_throttles()` or a `throttle_classes` set on the viewset replaces the
  default. You can delete that code and rely on the default, or declare
  `throttle = Throttle(create="30/hour")`.
- **A honeypot.** A request that fills the field named by
  `KARNI_PUBLIC_CREATE_HONEYPOT_FIELD` (default `homepage`) is answered 202
  and saves nothing. `@karni/ui`'s `ResourceForm` renders it hidden. A model
  with a field of that name keeps the field and gets no honeypot.
- **No anonymous imports.** The import endpoints of such a viewset need a
  signed-in user, who still has to pass `create` or `write`. In 0.4.0 an
  anonymous caller could import a file of rows through a public form.

What to do: if a public endpoint legitimately takes more than 10 creates an
hour from one caller (an integration posting from one server, say), raise
its limit with `throttle = Throttle(create="500/hour")`, turn it off with
`Throttle(create=None)`, or change `KARNI_PUBLIC_CREATE_RATE` for every
viewset (`None` turns the default off). The pytest plugin now starts each
test with empty rate-limit counters, so a suite that posts to a public form
many times keeps passing. See [rate limits](../api.md#rate-limits).

### Security headers on every response

`karni.security.SecurityHeadersMiddleware` is now in the `MIDDLEWARE` that
`karni_settings()` builds. Every response carries a Content-Security-Policy
and a Permissions-Policy. With `DEBUG` on the policy is report-only, so
development keeps working and the browser console lists what production
would block. With `DEBUG` off it is enforced.

The default policy allows what Karni serves: the admin, the browsable API,
the API docs pages, the welcome page and the `@karni/ui` app. A project page
that loads a script, stylesheet or font from another host (Google Fonts,
analytics, a map), or runs an inline script, is blocked in production until
the policy allows it:

```python
# config/settings.py, after karni_settings(globals())
KARNI_CSP = {
    "style-src": ["https://fonts.googleapis.com"],
    "font-src": ["https://fonts.gstatic.com"],
}
```

What to do: open the project's pages with `DEBUG` on and read the browser
console for `Content-Security-Policy-Report-Only` reports. Add each host
they name to `KARNI_CSP`, or allow one view's extra sources with
`@csp_extend`. If your proxy already sends a policy, set `KARNI_CSP = None`.
A project that defines `MIDDLEWARE` itself, after `karni_settings()`,
does not get the middleware: add `"karni.security.SecurityHeadersMiddleware"`
after Django's `SecurityMiddleware`. See
[security headers](../security.md#security-headers).

### Deploy checks

`karni check --deploy` runs Django's and Karni's deploy checks
(`karni.W510` to `karni.W520`) with whatever environment it is given, and
fails on any warning. Run it once with the production environment before the
next release. With the scaffold's development values it reports `DEBUG`, the
`SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, HSTS, the cookies,
the admin path, CORS, the content security policy and email, each with its
fix.
`CSRF_TRUSTED_ORIGINS` is now read from the environment (comma-separated),
and `SECURE_HSTS_SECONDS` too in the production profile. See
[deploy checks](../security.md#deploy-checks).

### A marker for project routes in config/urls.py

A new project's `config/urls.py` carries a `# karni:urls` line inside
`urlpatterns`, before `*welcome_urls()`:

```python
urlpatterns = [
    ...,
    *media_urls(),
    # Project routes that `karni make` wires (a public site's include goes here).
    # karni:urls
    # Only while DEBUG is on, and only until a route above answers "/".
    *welcome_urls(),
]
```

`karni make site <app>` inserts `path("", include("<app>.urls"))` at that
line, so a [public site](../public-site.md) replaces the welcome page, and
`karni make view` inserts routes at the same marker inside the site app's
own `urls.py`. The codemod adds the two lines to a `config/urls.py` that has
`*welcome_urls()` and no marker. A URLconf without `*welcome_urls()` is
listed for you: put the `# karni:urls` line after your own routes, where an
include at `""` may go. Without the marker, `karni make site` stops with the
line to add by hand.

### The agent files: run `karni rules sync`

The generated `AGENTS.md` and the other adapters now say where app screens
and a public site go. Rules K302 and K306 say they are about app screens,
the new rule K309 covers public server-rendered pages, and the `new-page`
procedure points at it. Until you run `karni rules sync`, `karni rules sync
--check` (and `make check`) reports the files as stale.

### `karni seed` refuses tables that already hold rows

`karni seed` now prints the models it will write to, then refuses with
`E617` (`karni explain E617`) when one of their tables already holds rows. A
seeded row carries no mark, so seed cannot tell its own rows from real
content, and demo rows added on top of content cannot be told apart later.
The user table is left out, so a fresh project with a superuser still seeds
without flags, and `--model` narrows the check to the tables it seeds.

What to change:

- A script or Makefile target that seeds the same database more than once:
  use `karni seed --reset`, which wipes the project's tables first. The
  reference application's end-to-end script already does.
- A script that seeds after loading or creating rows on purpose: add
  `--force`.
- `karni.seeding.seed()` does not refuse. Call
  `karni.seeding.occupied(seed_plan())` first if your code wants the same
  rule.

Real content (a site's copy and images) belongs in a content file loaded
with the new [`karni load`](../content-loading.md), which is safe to run on
every deploy.

### Settings the call reads fail loudly below it

`karni_settings(globals())` reads nine settings during the call to compute
others: `KARNI_AUTH_MODE`, `KARNI_2FA`, `KARNI_SOCIAL_AUTH` and
`KARNI_SOCIAL_PROVIDERS` decide `INSTALLED_APPS` and `MIDDLEWARE`,
`KARNI_FRONTEND_URL` feeds `CSRF_TRUSTED_ORIGINS`, `KARNI_AUTH_THROTTLE_RATES`
the throttle rates, `KARNI_JSON_LOGS` builds `LOGGING`, `KARNI_CACHE` builds
`CACHES` and `KARNI_STORAGE` builds `STORAGES`. In 0.4.0 one of them
assigned below the call was accepted and changed nothing, so a project could
run with `KARNI_AUTH_MODE = "session"` in its settings and JWT wiring. From
0.4.1 startup fails with [`karni.E508`](../errors.md#e508-a-setting-is-assigned-where-it-cannot-take-effect), which names the
setting and what was computed from it.

What to do: move the assignment above the `karni_settings(globals())` line,
pass it as a keyword (`karni_settings(globals(), KARNI_AUTH_MODE="session")`)
or set its variable in `.env`. The list is in
[settings](../settings.md#settings-read-during-the-call), and `KARNI_CACHE` and
`KARNI_STORAGE` defined above the call now build `CACHES` and `STORAGES` as
the environment variables do. Every other setting works below the call.

### The admin logo works wherever it is assigned, and on the login screen

`KARNI_ADMIN_LOGO` was read during the call, so a value assigned below it was
ignored without a word. The admin now reads it on every request:
`UNFOLD["SITE_LOGO"]` and `UNFOLD["SITE_ICON"]` hold
`karni.conf.admin_logo.site_logo` and `site_icon`, which unfold calls with
the request. The login screen shows the same logo above its title through
`karni_admin/login.html`, which `karni.admin` sets as the admin site's
`login_template` unless the site has one.

What to do: nothing for a project that sets the logo above the call or in
`.env`. A project that replaces `UNFOLD` below the call (`UNFOLD = {...}`)
while `KARNI_ADMIN_LOGO` is set now fails with `karni.E508`: change `UNFOLD`
in place, or add the two entries to yours. A site with its own
`login_template` keeps it. `unfold_logo_entries()` still exists for a project
that builds `UNFOLD` itself.

### `karni make model` adds the images extra to pyproject.toml

An `ImageField` needs Pillow, which the `karni[images]` extra installs. In
0.4.0 `karni make model ... photo:image` printed a note. It now changes the
`karni` requirement in `[project].dependencies` to `karni[images]`, keeping
its version spec, markers and other extras (`karni[s3]>=0.4` becomes
`karni[s3,images]>=0.4`), prints the change, and says to reinstall
(`pip install -e .`, or `docker compose build`). Only that one string
changes, `--dry-run` shows it in the diff, and a project that lists the extra
already is left alone. When `karni` is not a direct dependency the note
names the step instead.

### One dev port: `KARNI_DEV_PORT`

`KARNI_DEV_PORT` in `.env` (default 8000) is the port `karni serve --local`
runs Django on, the port the scaffold's `frontend/vite.config.ts` proxies
`/api` and `/health` to, and the port `docker-compose.yml` publishes Django
on. The config reads it from `../.env` or the environment with Vite's
`loadEnv`. `KARNI_API_PROXY` still wins when it is set, which is how the
compose stack points the frontend container at `django:8000`.

A 0.4.0 project's `vite.config.ts` keeps working: it proxies to port 8000,
and `karni serve --local` prints the `KARNI_API_PROXY=... npm run dev` line
whenever the server and the proxy disagree. To adopt the setting, replace
the `const target = ...` line and the `defineConfig({...})` call with the
scaffold's `defineConfig(({ mode }) => {...})` form (a fresh `karni new`
shows it), add the commented `KARNI_DEV_PORT` line to `.env.example`, and
publish `"${KARNI_DEV_PORT:-8000}:8000"` in `docker-compose.yml`.

### A site app's runtime is the karni-site module

`karni make site` now installs the `karni-site` module the way `karni add
site` does (the dependency in `pyproject.toml`, `karni_site` in the
`# karni:apps` block, its redirect middleware in the `# karni:middleware`
block and its `site` context processor), sets `handler404` and
`handler500` in `config/urls.py` to its error views, and writes
`templates/500.html`. The module brings the `{% ifactive %}` tag for the
current menu item, the `{% csp_hash %}` and `{% csp_allow %}` tags for a
design's inline scripts and other origins under the
Content-Security-Policy, the error views that render the site's own pages
with the request, and everything the client edits in the admin (blocks,
menus, the site's details, redirects, page titles). It has tables, so run
`karni migrate` after installing it.

A site app created with an earlier 0.4.1 build keeps working. To get the
missing pieces, install the module and let the generator add what is not
there:

```sh
pip install karni-site       # or add it to pyproject.toml and rebuild
karni make site <app> --force
karni add site               # records the module's agent guidance
karni migrate
```

`--force` creates only the missing files (`templates/500.html`) and adds
the wiring. Existing files are kept. Then load the tags where you want
them: `{% load static karni_site %}` at the top of `base.html`, and
`{% ifactive "<app>:<name>" %}` around the class or attribute each menu
link uses for the current page. The [karni-site README](../modules.md)
has the details.

### The staff app requires sign-in and opens on a dashboard

A project scaffolded by `karni new` 0.4.1 has a `frontend/src/layout.tsx`
that wraps every page but a sign-in page in `<AuthGuard explain>` (a visitor
who is not signed in sees the sign-in prompt in place), builds its menu with
`@karni/ui`'s `routeNavItems` and offers "Sign out", and a
`frontend/src/pages/home.tsx` that renders `<Dashboard>`: the counts and
newest rows of every model that declares `class Karni: dashboard = {...}`
([API: the staff dashboard](../api.md#the-staff-dashboard)).

A project scaffolded earlier keeps its own two files, which still work. To
adopt the new ones, scaffold a throwaway project (`karni new tmp`) and copy
`frontend/src/layout.tsx` and `frontend/src/pages/home.tsx` over yours
(`frontend/src/api/health.ts` is no longer needed), then give the models
that belong on the home page a `dashboard` declaration.

### The admin wears the project's karni-theme.css

`karni_settings()` now sets `KARNI_THEME_CSS` to
`frontend/src/karni-theme.css` and serves that file to the admin as
`karni/project-theme.css`, loaded third in `UNFOLD["STYLES"]`
([theming](../theming.md#one-theme-for-the-staff-app-and-the-admin)).

What to change:

- A project that appended a stylesheet of `--karni-*` overrides to
  `UNFOLD["STYLES"]` for the admin can drop it, if the frontend's
  `karni-theme.css` holds the same values.
- A project that defines `STATICFILES_FINDERS` itself adds
  `"karni.admin.theme.ProjectThemeFinder"` to it, or the admin's `<link>`
  answers 404. `KARNI_THEME_CSS = ""` turns the project theme off instead.
- A `karni-theme.css` that references the frontend's own variables (a
  shadcn/ui project) has no effect in the admin, which does not define them.
  `karni ui detect --css` writes literal values.

### karni-theme.css keeps dark mode

`karni ui detect` now writes a light-only colour under `:root:not(.dark)`.
In 0.4.0 it wrote `:root`, which has the same specificity as `@karni/ui`'s
`.dark` block and comes later, so the light colours also applied in dark
mode. A `karni-theme.css` written by 0.4.0 keeps that behaviour until it is
regenerated: run `karni ui detect --force` (the same sources, the new
blocks), or change its `:root {` colour block to `:root:not(.dark) {` by
hand.

### A production stack: `karni make deploy compose`

A new project gets `docker-compose.prod.yml`, a `Caddyfile` that a service
finally runs, and `.env.prod.example`: a one-shot `release` service, `django`
under gunicorn with uvicorn workers, Celery `worker` and `beat`, `caddy` with
automatic TLS, `db`, `redis` and a `backup` service, with health checks,
restart policies and named volumes. Every container from the production
image runs `karni check --deploy` first and refuses to start while it fails
(`E520`). [Deploying to a server](../deploy.md) is the walk-through.

A 0.4.0 project keeps working as it is. To adopt the stack:

1. Copy the `staff-app` and `backup` stages and the `prod` stage's
   `COPY --from=staff-app` line and `ENTRYPOINT` from a fresh project's
   `Dockerfile` (`karni new` in a scratch folder).
2. Add the `basepath` line to `frontend/src/routes.tsx` (next section).
3. Run `karni make deploy compose --force`. It replaces the `Caddyfile` and
   adds `.env.prod` to `.gitignore` and `.dockerignore`. It stops with `C105`
   when the `Dockerfile` still lacks a target it needs.

`KARNI_HEALTH_CHECKS` is now read from the environment (comma-separated), so a
deployment without a Celery worker leaves the Celery check out in `.env.prod`.

### The staff app follows Vite's base path

The production stack serves the staff app under `/app/`, so the build uses
that path as Vite's base, and the router has to know it. The scaffold's
`frontend/src/routes.tsx` now creates the router with it:

```ts
export const router = createRouter({
    routeTree: root.addChildren(routes),
    basepath: import.meta.env.BASE_URL,
});
```

In development the base is `/`, so nothing changes there. Add the line to a
0.4.0 project before serving its staff app under a path.

### The agent files name `karni make form`

Rule K309 and the `new-model` procedure now tell an agent that a public
form is `karni make form <name> <field:type> ... [--notify SETTING]` plus
`{% karni_form "<name>" %}` in the page, and never a hand-written form view,
throttle or form script. Run `karni rules sync`. Until you do, `karni rules
sync --check` reports the files as stale.

A form a project wrote by hand keeps working. To move one to the generated
form, keep its model and viewset (a viewset with `create=Public()` needs no
throttle of its own since this release), put `{% load karni_site %}` and
`{% karni_form "<model name>" %}` where the page's `<form>` was, include
`karni_site.urls` in `config/urls.py` (`path("", include("karni_site.urls"))`
before the site's own include), and delete the form's script. For the
email, call `karni_site.notify.notify_recipients` from the listener. See
[public forms](../public-site.md#public-forms).

### A procedure from a design to content: run `karni rules sync`

The new `site-from-design` procedure (`karni rules --procedure
site-from-design`) gives an agent the steps from a designer's pages to a
site with real content: `karni import design`, `karni design analyze` (the
models the repeated content needs, and the decisions the markup cannot
settle), the `karni make model` commands, `karni design extract`, `karni
load` and templates that loop over the rows. See [From a design to
content](../design-content.md). Run `karni rules sync` to add its slash
command files. Until then `karni rules sync --check` (and `make check`)
reports the files as stale.

### The admin is light only

The admin used to follow the system's light or dark preference, with a
switch in the sidebar. It now shows the light palette on every page and the
login screen, with no switch, through the new setting `KARNI_ADMIN_THEME`
(default `"light"`).

What to do: nothing to keep the new default. To keep the old behaviour, set
`KARNI_ADMIN_THEME = "auto"` (or `KARNI_ADMIN_THEME=auto` in `.env`).
`"dark"` pins the dark palette. A project that sets `UNFOLD["THEME"]`
itself keeps its own value. See [admin theming](../admin.md#theming).

### Projects have a kind

`karni new` asks what kind of project it is, or takes `--kind`: `site` (a
public website the client edits in the admin), `app` (an API and a React
app, what `karni new` always made) or `site+app`. It records the answer in
pyproject.toml:

```toml
[tool.karni]
kind = "app"
```

`karni context` prints it on its first line and the agent files state it
with its stack. A project made before this has no `kind`, and Karni reads
the kind its files show: `karni_site` in the `# karni:apps` block makes a
site (a site+app with a `frontend/`), anything else an app. Add the line to
say it yourself. A value Karni does not know fails `karni context` and
`karni rules sync` with C112.

An app that gets a public website runs `karni add site`. It wires karni-site
as before and sets `kind = "site+app"`, then `karni make site website` or
`karni import design` makes the site app. `karni make site` and `karni
import design` set the kind the same way when they wire the module. To go
back, set `kind = "app"` again and run `karni rules sync`. The site's files
stay until you delete them: the site app and its include in
`config/urls.py`, karni-site in pyproject.toml, and `karni_site` with its
middleware and context processor in config/settings.py. See
[start a site project](../public-site.md#start-a-site-project).

### The agent files state the kind: run `karni rules sync`

AGENTS.md and the other adapters open with the project's kind and its stack,
so an agent never asks which technology to use. The `site-from-design`
procedure is the whole flow now: `karni design analyze` first, then `karni
import design --editable --map content/design-map.json` (the content the map
reads into rows gets no blocks, because the loops render it from the rows),
the models, the content, the loops, `karni make form` for each `<form>`, the
page test and `karni check`. Run `karni rules sync`. Until then `karni rules
sync --check` (and `make check`) reports the files as stale.

A site imported before with `--editable` and no map keeps its blocks. Where
a template now loops over rows, take the `{% editable %}` tags out of the
markup inside the loop, or import again with `--map` before you edit the
templates.

### Search engines: `{% karni_seo %}`, sitemap.xml and robots.txt

A site app's `base.html` now has `{% karni_seo %}` in its head, around the
title and description:

```django
{% karni_seo %}<title>{% block title %}{{ site.name }}{% endblock %}</title>
<meta name="description" content="{% block description %}{% endblock %}">{% block seo %}{% endblock %}{% endkarni_seo %}
```

It writes the canonical link, the share tags and the site's JSON-LD, so
remove the `<link rel="canonical">` an earlier `base.html` had. And
`config/urls.py` includes karni_site's URLs before the site's own:

```python
path("", include("karni_site.urls")),
```

which answer `/robots.txt` (closed to crawlers unless `DJANGO_ENV` is
`prod`, or `KARNI_SITE_ALLOW_INDEXING` says otherwise) and `/sitemap.xml`.
`karni add site` adds the include to an existing project, and so does
`karni make site <app> --force`. Then `karni check --seo` renders every
page and reports what search engines would find missing. Install the
module's images extra for the smaller copies of uploaded images:
`pip install "karni-site[images]"`.

### The design's images are sized

`karni import design` now writes `width` and `height` on the design's
`<img>` tags that lack them, from each image's own file, and marks them
`data-karni-image`, which `{% karni_seo %}`'s CSS keeps in proportion
(`height: auto`). Where Pillow is installed it also writes smaller WebP
copies of each large JPEG, PNG or WebP next to it under `static/<app>/`
(`hero.jpg.640w.webp`) and a `srcset` and `sizes` that use them. The next
import of a design changes the templates the project has not edited since
the last one, and keeps the edited ones as before. Without Pillow
(`pip install pillow` where `karni` runs) only the sizes are written.


### Grants open admin pages

In 0.4.0 a staff user opened a model's admin page only with Django's model
permission for it, and the role groups `karni sync-roles` creates carry
none. A staff user with the `staff` role, which grants everything, got a 403
on the project's own models. Now a role's grant (`app.model:<action>`) opens
the page for that action, inside the grant's scope and unless a veto refuses
it. Django's model permissions still open pages for a user without a grant,
superusers open everything, and the admin index lists exactly the models
the user may open.

This widens who can open admin pages. Before you upgrade:

- List who has staff status (`is_staff`) and which roles each person holds.
  Every staff user with the `staff` role now opens every Karni admin page,
  users and roles included.
- A grant on the user model lets its holder change accounts and give
  roles. Only a superuser changes `is_superuser` or `user_permissions`, or
  edits or deletes a superuser's account.
- Signing in still needs `is_staff`. A role alone gives no admin access.

To keep the 0.4.0 rule (Django's model permissions open pages, the grants
decide the rows), set it after `karni_settings()`, or in `.env`:

```python
KARNI_ADMIN_GRANTS_OPEN_PAGES = False
```

`karni_site.admin.GrantedAdminMixin` and `GrantedInlineMixin`, which did the
same for the site module's own pages, are gone: every Karni admin has the
behaviour, and `karni.admin.KarniInlineMixin` gives it to an inline of your
own. See [who may open a page](../admin.md#who-may-open-a-page).

### Tests run on an empty local-memory cache

In 0.4.0 a project's tests used the project's own cache, Redis at
`REDIS_URL`, the one the development server uses. Throttle counters, a
listener's "already queued" flag and anything else a test cached stayed
there for the next test, the next run and the dev server, so tests failed
at random. Now Karni's pytest plugin gives every test an empty
local-memory cache for each alias in `CACHES`, and the tests of a new
project never connect to Redis.

A test that relied on a value an earlier test cached now finds the cache
empty: set the value up in the test or a fixture. A test that needs Redis
itself keeps the project's cache:

```python
@pytest.mark.karni_project_cache
def test_the_lock_is_shared_between_workers():
    ...
```

`karni_test_cache = project` under `[tool.pytest.ini_options]` keeps the
project's cache for every test, as in 0.4.0. A `conftest.py` fixture that
swapped `CACHES` for a local-memory cache can go. See
[the cache in tests](../testing.md#the-cache-in-tests).

### Files under the project in development

In 0.4.0 `MEDIA_ROOT` and `STATIC_ROOT` defaulted to `/data/media` and
`/data/static` in every profile, and `.env.example` set them too. That
folder exists only in the container, so a project run on the host
(`karni serve --local`) could not store an upload. Now the dev profile
stores them under the project: `data/media` and `data/static` next to
`manage.py`, which `.gitignore` already leaves out. A relative value, in
`.env` or from the default, is read from the project root (`BASE_DIR`, else
the folder above `config/`), whatever folder a command runs from. The prod
profile keeps `/data/media` and `/data/static`.

A project made with 0.4.0 keeps working as it is: its `.env` sets
`/data/media`. To get the new default on the host, give the containers the
`/data` paths first, in the Dockerfile's `base` and `prod` stages:

```dockerfile
ENV MEDIA_ROOT=/data/media \
    STATIC_ROOT=/data/static
```

and then remove `MEDIA_ROOT` and `STATIC_ROOT` from `.env` (or set them to
`data/media` and `data/static`). `karni make deploy compose` already writes
the `/data` paths into `.env.prod`.

### The frontend moves to Zod 4

`npm install` in a 0.4.0 project's `frontend/` reports two high-severity
findings: Zod before 4.6.6 can exhaust memory validating an oversized
collection ([GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)),
and `@karni/ui` depends on it. A new project's `frontend/package.json` now
has:

```json
"@hookform/resolvers": "^5.2.0",
"react-hook-form": "^7.55.0",
"zod": "^4.6.6"
```

`@karni/ui` 0.4.1 accepts Zod 3 (3.23 or later) and Zod 4 (4.6.6 or later),
with `@hookform/resolvers` 3 or 5, so an earlier project keeps working
without a change. To clear the audit, set the three lines above in
`frontend/package.json` and run `(cd frontend && npx --yes npm@11 install)`.
Code of your own that builds Zod schemas may need changes first: Zod 4
drops `required_error` and `invalid_type_error` (pass `{ message }` or
`{ error }`), and reads a failure's `issues` rather than `errors`. Zod's
own migration guide lists the rest. Then run `npm run build` and `karni
check` in the project.

### Production email: `EMAIL_URL` and `karni.W520`

`karni_settings()` reads the mail server from `EMAIL_URL`
(`smtp+tls://user:password@smtp.example.com:587`, `smtps://` for SSL), and
`DEFAULT_FROM_EMAIL` and `SERVER_EMAIL` from the environment. A project that
sets none of them keeps Django's defaults, and development still prints mail
to the console unless `EMAIL_URL` names a server. A project that assigns the
`EMAIL_*` settings in `config/settings.py` keeps its own values.

`karni check --deploy`, which the production containers run before they
start, now reports `karni.W520` while production email goes nowhere: the
console, locmem, dummy or file backend, or a sender at localhost (Django's
`webmaster@localhost`). Before the next deploy, add the two lines to
`.env.prod`:

```sh
EMAIL_URL=smtp+tls://user:password@smtp.example.com:587
DEFAULT_FROM_EMAIL=noreply@example.com
```

A project that sends no email adds the code to `config/settings.py` instead:
`SILENCED_SYSTEM_CHECKS += ["karni.W520"]`. A new project's
`.env.prod.example` lists the email settings, commented out.

### The development worker: threads on a Mac, and a broker timeout

`karni worker` on a Mac now runs Celery's `threads` pool. It ran `solo` in
0.4.0, which runs one task at a time and stops answering `celery inspect`
and the health check's ping while a task runs. Celery's default `prefork`
pool fails every task on macOS: billiard 4.3 starts its processes with
`spawn` there, and Celery rebuilds its task state in a spawned process only
on Windows. `--pool` (or `-P`) picks another pool, for example
`karni worker --pool solo`. On Linux and in Docker, Celery's `prefork` stays
the default.

The dev profile now sets `CELERY_BROKER_TRANSPORT_OPTIONS = {"socket_timeout": 5}`.
At a warm shutdown, Celery's Redis transport reads the answer to the worker's
last BRPOP without a timeout. A Redis that never sends it, such as a
long-running Redis on a Mac whose timers stalled, kept the worker in "Warm
shutdown" until it was killed. With the timeout the worker exits within about
six seconds. The prod profile keeps Celery's default. A project that sets
`CELERY_BROKER_TRANSPORT_OPTIONS` itself keeps its own value: add
`"socket_timeout": 5` to it for the same bound in development.

### Menus that list a model's rows

A menu item with *children from* a model and neither a title nor an address
now lists the model's rows in its own place: a footer that lists every
service is one such item. In 0.4.0 the same item rendered as an entry with an
empty link and the rows as its children. Give the item a title, or an
address, to keep the old shape.

`karni import design --editable --map` seeds a list whose links are exactly
one model's detail pages (every one, once, by its title) as that model's
rows: the seed template marks the list with
`data-karni-children-from="<app>.<Model>"`, and the import's report names
each menu. A menu the database already has keeps its items: delete it in the
admin to have it seeded again from the new template.
