# Migrating to Karni 0.4.1

Every change below is recorded in Karni's machine-readable changelog
(`packages/karni/karni/changelog/0.4.1.toml`). Nothing here breaks a 0.4.0
project's build or tests. `karni upgrade` adds the URL marker, reports
anything it could not place, and lists the public-read viewsets to review and
the agent files to regenerate. Changing who may write a resource is the
project's decision, so no codemod touches access. `karni check` may print a
new warning.

## Upgrading

```bash
pipx upgrade karni-cli        # the CLI carries the changelog
karni upgrade --dry-run       # shows the diff and the notes below, writes nothing
karni upgrade                 # applies the codemod on a clean git tree
# then pin karni to 0.4.1 in pyproject.toml, reinstall, and run:
karni rules sync              # rewrite the agent files
karni check                   # prints karni.W102 for each viewset to review
karni check --deploy          # before going live, with production settings
```

## Changed in 0.4.1

### Public-read viewsets: review who may write

This is a security fix. In 0.4.0, `karni make model ... --access public-read`
and `karni make viewset ... --access public-read` wrote this declaration:

```python
access = Access(read=Public(), write=Authenticated())
```

A new project also has open self-registration (`POST /api/auth/register/`).
Together they let anyone who opens an account create, change and delete
every row of the resource through the API. The test `karni make test`
generated acted as any signed-in user, so it passed and did not catch it.
The problem was found in a real project built on 0.4.0.

From 0.4.1, `--access public-read` writes:

```python
access = Access(read=Public(), write=HasRole("staff"))
```

`staff` is the system role in the default `KARNI_ROLES`.
`--access public-read:<role>` names another role, for example
`public-read:editor`. `karni make test` now acts as the role the `write`
predicate names, so the generated test really creates, updates and deletes.

What to do in a 0.4.0 project:

1. Run `karni check`. Each viewset whose `write` lets every signed-in user
   change every row is reported as [karni.W102](../errors.md#w102-any-self-registered-user-may-change-and-delete-every-row-of-a-resource).
2. For each one, decide who may write and change `write`. Use
   `HasRole("staff")` (what the preset writes now), `Granted()` (the roles'
   grants) or `Owned("<field>")` (rows the user owns).
3. If a generated test now fails because its user cannot write, pass the
   role: `self.assert_crud(VenueViewSet, "staff")`, or regenerate it with
   `karni make test Venue --force`.

`create=Authenticated()` with an owned `write` (anyone signed in may add a
row, and only its owner may change it) is the normal pattern for content
users create, and W102 does not report it.

### Self-registration can be turned off

`KARNI_ACCOUNTS_REGISTRATION` (default `True`, so nothing changes) decides
whether anyone may open an account. `False` leaves `register/` out of the
URLs, so it answers 404 and is absent from the OpenAPI schema. Use it when
staff create every account, for example a brochure site with a CMS. W102
is silent while registration is off. See
[closing registration](../accounts.md#closing-registration).

If every signed-in user is trusted to write and W102 is wrong for your
project, add `"karni.W102"` to `SILENCED_SYSTEM_CHECKS`.

### Public creates are rate-limited

A viewset whose `create` anyone may call (`create=Public()`, or
`write=Public()` without a `create`) now gets three protections without a
line of code:

- **A rate limit.** Each caller (the user, else the client IP) may create
  `KARNI_PUBLIC_CREATE_RATE` rows, default 10 an hour. Over it, `create`
  answers 429 with `Retry-After`. A 0.4.0 project that wrote its own
  `get_throttles()` for a contact form keeps it: an overridden
  `get_throttles()` or a `throttle_classes` set on the viewset replaces the
  default. You can delete that code and rely on the default, or declare
  `throttle = Throttle(create="30/hour")`.
- **A honeypot.** A request that fills the field named by
  `KARNI_PUBLIC_CREATE_HONEYPOT_FIELD` (default `homepage`) is answered 202
  and saves nothing. `@karni/ui`'s `ResourceForm` renders it hidden. A model
  with a field of that name keeps the field and gets no honeypot.
- **No anonymous imports.** The import endpoints of such a viewset need a
  signed-in user, who still has to pass `create` or `write`. In 0.4.0 an
  anonymous caller could import a file of rows through a public form.

What to do: if a public endpoint legitimately takes more than 10 creates an
hour from one caller (an integration posting from one server, say), raise
its limit with `throttle = Throttle(create="500/hour")`, turn it off with
`Throttle(create=None)`, or change `KARNI_PUBLIC_CREATE_RATE` for every
viewset (`None` turns the default off). The pytest plugin now starts each
test with empty rate-limit counters, so a suite that posts to a public form
many times keeps passing. See [rate limits](../api.md#rate-limits).

### Security headers on every response

`karni.security.SecurityHeadersMiddleware` is now in the `MIDDLEWARE` that
`karni_settings()` builds. Every response carries a Content-Security-Policy
and a Permissions-Policy. With `DEBUG` on the policy is report-only, so
development keeps working and the browser console lists what production
would block. With `DEBUG` off it is enforced.

The default policy allows what Karni serves: the admin, the browsable API,
the API docs pages, the welcome page and the `@karni/ui` app. A project page
that loads a script, stylesheet or font from another host (Google Fonts,
analytics, a map), or runs an inline script, is blocked in production until
the policy allows it:

```python
# config/settings.py, after karni_settings(globals())
KARNI_CSP = {
    "style-src": ["https://fonts.googleapis.com"],
    "font-src": ["https://fonts.gstatic.com"],
}
```

What to do: open the project's pages with `DEBUG` on and read the browser
console for `Content-Security-Policy-Report-Only` reports. Add each host
they name to `KARNI_CSP`, or allow one view's extra sources with
`@csp_extend`. If your proxy already sends a policy, set `KARNI_CSP = None`.
A project that defines `MIDDLEWARE` itself, after `karni_settings()`,
does not get the middleware: add `"karni.security.SecurityHeadersMiddleware"`
after Django's `SecurityMiddleware`. See
[security headers](../security.md#security-headers).

### Deploy checks

`karni check --deploy` runs Django's and Karni's deploy checks
(`karni.W510` to `karni.W519`) with whatever environment it is given, and
fails on any warning. Run it once with the production environment before the
next release. With the scaffold's development values it reports `DEBUG`, the
`SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, HSTS, the cookies,
the admin path, CORS and the content security policy, each with its fix.
`CSRF_TRUSTED_ORIGINS` is now read from the environment (comma-separated),
and `SECURE_HSTS_SECONDS` too in the production profile. See
[deploy checks](../security.md#deploy-checks).

### A marker for project routes in config/urls.py

A new project's `config/urls.py` carries a `# karni:urls` line inside
`urlpatterns`, before `*welcome_urls()`:

```python
urlpatterns = [
    ...,
    *media_urls(),
    # Project routes that `karni make` wires (a public site's include goes here).
    # karni:urls
    # Only while DEBUG is on, and only until a route above answers "/".
    *welcome_urls(),
]
```

`karni make site <app>` inserts `path("", include("<app>.urls"))` at that
line, so a [public site](../public-site.md) replaces the welcome page, and
`karni make view` inserts routes at the same marker inside the site app's
own `urls.py`. The codemod adds the two lines to a `config/urls.py` that has
`*welcome_urls()` and no marker. A URLconf without `*welcome_urls()` is
listed for you: put the `# karni:urls` line after your own routes, where an
include at `""` may go. Without the marker, `karni make site` stops with the
line to add by hand.

### The agent files: run `karni rules sync`

The generated `AGENTS.md` and the other adapters now say where app screens
and a public site go. Rules K302 and K306 say they are about app screens,
the new rule K309 covers public server-rendered pages, and the `new-page`
procedure points at it. Until you run `karni rules sync`, `karni rules sync
--check` (and `make check`) reports the files as stale.

### `karni seed` refuses tables that already hold rows

`karni seed` now prints the models it will write to, then refuses with
`E617` (`karni explain E617`) when one of their tables already holds rows. A
seeded row carries no mark, so seed cannot tell its own rows from real
content, and demo rows added on top of content cannot be told apart later.
The user table is left out, so a fresh project with a superuser still seeds
without flags, and `--model` narrows the check to the tables it seeds.

What to change:

- A script or Makefile target that seeds the same database more than once:
  use `karni seed --reset`, which wipes the project's tables first. The
  reference application's end-to-end script already does.
- A script that seeds after loading or creating rows on purpose: add
  `--force`.
- `karni.seeding.seed()` does not refuse. Call
  `karni.seeding.occupied(seed_plan())` first if your code wants the same
  rule.

Real content (a site's copy and images) belongs in a content file loaded
with the new [`karni load`](../content-loading.md), which is safe to run on
every deploy.

### Settings the call reads fail loudly below it

`karni_settings(globals())` reads nine settings during the call to compute
others: `KARNI_AUTH_MODE`, `KARNI_2FA`, `KARNI_SOCIAL_AUTH` and
`KARNI_SOCIAL_PROVIDERS` decide `INSTALLED_APPS` and `MIDDLEWARE`,
`KARNI_FRONTEND_URL` feeds `CSRF_TRUSTED_ORIGINS`, `KARNI_AUTH_THROTTLE_RATES`
the throttle rates, `KARNI_JSON_LOGS` builds `LOGGING`, `KARNI_CACHE` builds
`CACHES` and `KARNI_STORAGE` builds `STORAGES`. In 0.4.0 one of them
assigned below the call was accepted and changed nothing, so a project could
run with `KARNI_AUTH_MODE = "session"` in its settings and JWT wiring. From
0.4.1 startup fails with [`karni.E508`](../errors.md#e508-a-setting-is-assigned-where-it-cannot-take-effect), which names the
setting and what was computed from it.

What to do: move the assignment above the `karni_settings(globals())` line,
pass it as a keyword (`karni_settings(globals(), KARNI_AUTH_MODE="session")`)
or set its variable in `.env`. The list is in
[settings](../settings.md#settings-read-during-the-call), and `KARNI_CACHE` and
`KARNI_STORAGE` defined above the call now build `CACHES` and `STORAGES` as
the environment variables do. Every other setting works below the call.

### The admin logo works wherever it is assigned, and on the login screen

`KARNI_ADMIN_LOGO` was read during the call, so a value assigned below it was
ignored without a word. The admin now reads it on every request:
`UNFOLD["SITE_LOGO"]` and `UNFOLD["SITE_ICON"]` hold
`karni.conf.admin_logo.site_logo` and `site_icon`, which unfold calls with
the request. The login screen shows the same logo above its title through
`karni_admin/login.html`, which `karni.admin` sets as the admin site's
`login_template` unless the site has one.

What to do: nothing for a project that sets the logo above the call or in
`.env`. A project that replaces `UNFOLD` below the call (`UNFOLD = {...}`)
while `KARNI_ADMIN_LOGO` is set now fails with `karni.E508`: change `UNFOLD`
in place, or add the two entries to yours. A site with its own
`login_template` keeps it. `unfold_logo_entries()` still exists for a project
that builds `UNFOLD` itself.

### `karni make model` adds the images extra to pyproject.toml

An `ImageField` needs Pillow, which the `karni[images]` extra installs. In
0.4.0 `karni make model ... photo:image` printed a note. It now changes the
`karni` requirement in `[project].dependencies` to `karni[images]`, keeping
its version spec, markers and other extras (`karni[s3]>=0.4` becomes
`karni[s3,images]>=0.4`), prints the change, and says to reinstall
(`pip install -e .`, or `docker compose build`). Only that one string
changes, `--dry-run` shows it in the diff, and a project that lists the extra
already is left alone. When `karni` is not a direct dependency the note
names the step instead.

### One dev port: `KARNI_DEV_PORT`

`KARNI_DEV_PORT` in `.env` (default 8000) is the port `karni serve --local`
runs Django on, the port the scaffold's `frontend/vite.config.ts` proxies
`/api` and `/health` to, and the port `docker-compose.yml` publishes Django
on. The config reads it from `../.env` or the environment with Vite's
`loadEnv`. `KARNI_API_PROXY` still wins when it is set, which is how the
compose stack points the frontend container at `django:8000`.

A 0.4.0 project's `vite.config.ts` keeps working: it proxies to port 8000,
and `karni serve --local` prints the `KARNI_API_PROXY=... npm run dev` line
whenever the server and the proxy disagree. To adopt the setting, replace
the `const target = ...` line and the `defineConfig({...})` call with the
scaffold's `defineConfig(({ mode }) => {...})` form (a fresh `karni new`
shows it), add the commented `KARNI_DEV_PORT` line to `.env.example`, and
publish `"${KARNI_DEV_PORT:-8000}:8000"` in `docker-compose.yml`.

### A production stack: `karni make deploy compose`

A new project gets `docker-compose.prod.yml`, a `Caddyfile` that a service
finally runs, and `.env.prod.example`: a one-shot `release` service, `django`
under gunicorn with uvicorn workers, Celery `worker` and `beat`, `caddy` with
automatic TLS, `db`, `redis` and a `backup` service, with health checks,
restart policies and named volumes. Every container from the production
image runs `karni check --deploy` first and refuses to start while it fails
(`E520`). [Deploying to a server](../deploy.md) is the walk-through.

A 0.4.0 project keeps working as it is. To adopt the stack:

1. Copy the `staff-app` and `backup` stages and the `prod` stage's
   `COPY --from=staff-app` line and `ENTRYPOINT` from a fresh project's
   `Dockerfile` (`karni new` in a scratch folder).
2. Add the `basepath` line to `frontend/src/routes.tsx` (next section).
3. Run `karni make deploy compose --force`. It replaces the `Caddyfile` and
   adds `.env.prod` to `.gitignore` and `.dockerignore`. It stops with `C105`
   when the `Dockerfile` still lacks a target it needs.

`KARNI_HEALTH_CHECKS` is now read from the environment (comma-separated), so a
deployment without a Celery worker leaves the Celery check out in `.env.prod`.

### The staff app follows Vite's base path

The production stack serves the staff app under `/app/`, so the build uses
that path as Vite's base, and the router has to know it. The scaffold's
`frontend/src/routes.tsx` now creates the router with it:

```ts
export const router = createRouter({
    routeTree: root.addChildren(routes),
    basepath: import.meta.env.BASE_URL,
});
```

In development the base is `/`, so nothing changes there. Add the line to a
0.4.0 project before serving its staff app under a path.
