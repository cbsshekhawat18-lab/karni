Everything below was observed in a project created with `karni new auditapp`

## Findings ranked by what they cost a real user

1. **`karni check` enforces nothing in a `karni new` project (claim f).** `karni_settings()` and the scaffold never define `BASE_DIR`; `karni.testing._source.project_app_configs()` then returns `[]`, so the `architecture` hook and `pytest --pyargs karni.testing.architecture` scan zero apps and every rule passes vacuously — including in `examples/eventhub`. A project with raw SQL, an HTTP client in a viewset, an unpaginated action and an `access` override got `karni check: ok` and 9 green tests. Adding one `BASE_DIR` line surfaced 5 violations. No test catches this: `tests/testing/test_architecture.py` monkeypatches `project_app_configs` to inject fixture apps, so the discovery path that decides whether anything is scanned is untested, and `grep BASE_DIR` finds no definition in `karni/conf`, the template, `examples/eventhub` or `karni/tests/settings.py`. The "every rule fails a build" promise, the CI gate and the quickstart's `karni check --no-frontend` step are all hollow until this is fixed (define `BASE_DIR` in `karni_settings()` or call `project_app_configs(infer_root=True)` like `karni seed` does). Evidence: `f-architecture-output.txt`, `f-basedir-experiment.txt`.
2. **`?search=` is a 500 on PostgreSQL (claim b).** The default provider emits `similarity()` (pg_trgm) and nothing creates the extension: not `karni migrate`, not `karni make model --search`, no system check, no scaffold migration. The quickstart hides it by running on SQLite (portable fallback). The first `karni make model … --search title` against the compose PostgreSQL gives every search request `ProgrammingError: function similarity(character varying, unknown) does not exist`. Evidence: `b-search-500-traceback.txt`, `b-curl-output.txt` B13.
3. **The generated form page cannot be submitted when the model has an optional FK without a route (claim d).** `Event.organizer` (nullable FK to User) is rendered as a free-text UUID input; left blank, the zod schema rejects it ("Invalid uuid") and no request is made, so the `--kind form` page for the quickstart's own `Event` model (`organizer:fk:User`) is dead on arrival without hand edits. Evidence: `d-shoot-report3.json`, `d-ui-event-new-form-after-submit.png`.
4. **The generated detail page shows relations as raw UUIDs (claim d).** `ResourceDetail` supports `expand`, but `karni make page --kind detail` does not pass it, so the "nested relation" promise holds for the table only. Evidence: `d-ui-event-detail.png`.
5. **MCP `context` fails from an MCP host (claim h).** `karni mcp` resolves the project interpreter only through `<project>/.venv` or an inherited `VIRTUAL_ENV`; the quickstart puts the venv in the parent directory, so Claude Code/Cursor launching `karni mcp` from `.mcp.json` gets `C002 "no .venv and the compose stack is not running"` for `context`, returned with `isError: false`. `rules` and `check` work. Evidence: `h-mcp-output.txt` vs `h-mcp-output2.txt`.
6. **Uploads are invisible in local dev (claim c).** `MEDIA_URL=/media/` is set but nothing serves it under `karni serve --local`; the derived admin's image preview and file links 404. Only the Caddy container serves `/media/*`. Evidence: `c-shoot-report.json` (product-change failed requests).
7. **`karni upgrade` over-reports on fresh projects (claim i).** Installed `karni` says 0.1.0 while the shipped changelog is 0.2.0, so a project scaffolded by this very CLI is told about 10 manual 0.2 changes it already satisfies. Cosmetic, but it trains users to ignore the manual section.
8. **Search is a silent no-op without `search_fields` (claim b).** `?search=x` returns 200 with every row and the schema omits the parameter; a client that forgets the declaration gets wrong results, not an error. Documented and tested, but a footgun.
9. **Smaller rough edges.** Enum descriptions are rendered as raw markdown help text under the form's status select; a required relation left empty says "Expected string, received null"; the relation column header renders as "VENUE" while the others are title-case; `/admin/login/` without `?next=` lands on a 404 at `/accounts/profile/`; the scaffold home page reports readiness "fail" (`/health/ready/` 503: no Celery worker) under `karni serve --local`; drf-spectacular logs two "unable to guess serializer" errors on every schema build; `karni rules` sits at 396 of its 400-token budget; `karni context` measured 254 tokens against the docs' "~200 for a typical project"; `karni new` from a checkout warns that the `@karni/ui` dist is stale (contributor-only). The `?deleted=all` admin changelist runs a duplicated query.

## Summary

The data layer and the generated API are genuinely as advertised: a model on `BaseModel` and a three-line viewset gave correct CRUD, filtering, ordering, pagination, expansion and an OpenAPI document with vendor extensions, the zero-code admin is complete and usable, the adapters regenerate byte-for-byte, `karni context` tracks the registry, and `karni upgrade` is a real, idempotent codemod with an honest dry run. The agent-facing fast path (`karni rules --check`, the MCP `rules`/`check` tools) is accurate and names fixes. What does not hold is the enforcement promise and the "it just works" edges a real user hits first: `karni check` is a no-op in every scaffolded project because `BASE_DIR` is never defined, `?search=` 500s on the default PostgreSQL stack until someone installs `pg_trgm` by hand, the generated form page for the quickstart's own `Event` model cannot be submitted, the generated detail page shows relations as UUIDs, and the MCP `context` tool fails unless the host happens to inherit an activated venv. Three of these (BASE_DIR, pg_trgm, the form's nullable FK) are one-line fixes with outsized cost to a first-time user, and the first of them means the CI gate the docs lean on has never actually guarded a project.
