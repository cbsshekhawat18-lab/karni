## Findings ranked by what they cost a real user (worst first)

1. **The quickstart app is dead past `karni check` without a Redis the page never mentions** (claim 3d). With the `.env` the page produces, `REDIS_URL` still points at the compose hostname `redis`; DRF's anon/user throttles (`karni/conf/base.py` `DEFAULT_THROTTLE_CLASSES`/`RATES`) read the Redis-backed cache on every request, so login, the OpenAPI schema, the Swagger page and even a `public-read` list all answer **500** with a Django error page. The page promises "no Docker required", then tells the user to sign in and create an Event — impossible as written. The scaffold's own README (`Without Docker` section) does say to set `REDIS_URL=redis://127.0.0.1:6379/0`; the quickstart does not, and neither says Redis must be running. A first-time user sees a stack of 500s on their first click. Evidence: `03-quickstart-api-probe.log`, `03-quickstart-api-docs-500-frames.txt`, `03-quickstart-serve.log`.
2. **`karni test` fails on the quickstart with "No module named pytest"** (claim 3c), exit 1, on the step whose caption is "`karni test` ran the generated tests". The page claims CI runs it verbatim; CI passes only because `.github/workflows/ci.yml:153` silently adds `pytest pytest-django` to the one substituted line. Users following the page hit a hard failure one command after their first success. Evidence: `03-quickstart-block3-seed-test-check.log`.
3. **`karni doctor` crashes with a traceback in the layout the quickstart creates** (claim 10) — the tool meant to diagnose environment problems is the one that blows up when the venv is outside the project. Evidence: `06-karni-doctor.log`.
4. **`karni --version` does not exist** (claim 2b): `No such option`, exit 2. A user or agent cannot tell which karni-cli they have without `pip show`. Evidence: `02-cli-smoke.log`.
5. **Readiness is 503 under the documented local command.** `karni serve --local` (the only non-Docker run command on the quickstart and in `karni new`'s hints) gives `/health/ready/` 503 and a "Backend readiness: fail" home page until a worker is started with `karni worker`, which no local-run doc mentions; `karni new`'s printed "Next steps" only offer `docker compose up -d`. Evidence: `04-stack-health.log` (first readiness), `04-stack-karni-new-testapp.log`.
6. **Postgres driver is not installed by any documented non-Docker step.** The generated `pyproject.toml` declares `psycopg[binary]`, but the quickstart's venv never gets it; pointing `DATABASE_URL` at Postgres fails until `pip install "psycopg[binary]"` is run by hand (needed here, `04-stack-backend-prepare.log`). The scaffold README's `uv pip install … -r pyproject.toml` would cover it; the quickstart's `pip install karni karni-cli` does not.
7. **PyPI install line fails** (claim 3a) — expected pre-publication; the page's substitute is documented and works (`03-quickstart-documented-editable-substitute.log`). Cost today: the first command on the page fails for everyone.
8. **`docker compose up` unverified here** (claim 4a). Nothing in this audit says anything about the compose stack, the Dockerfiles or Caddy.
9. **Stopping the `karni serve`/`karni worker` wrappers leaks the real servers.** SIGTERM to the wrapper leaves `manage.py runserver` (and its autoreload child) and the Celery worker running and listening. Interactive Ctrl-C is unaffected; scripts and agents that kill the wrapper PID leak ports. Evidence: `04-stack-timeline.log`.
10. **Cosmetic**: every `karni new` project ships `__pycache__/` dirs copied from pip's byte-compiled copy of the packaged template (`ticket_shop/__pycache__/manage.cpython-312.pyc` dated at scaffold time; gitignored, harmless). `karni seed`'s demo user is reported as "(staff)" but is a superuser. The scaffold frontend's `npm install` reports 9 vulnerabilities (3 moderate, 6 high) in dev dependencies. The karni-payments sdist carries the `ui/` sources.

## Summary

Packaging and installation are in good shape: the three wheels/sdists and both npm tarballs contain every runtime file in the source tree, a clean venv installs them and the CLI, error-code registry, bundled templates and links module all work from site-packages. The generated project also boots cleanly on a host Postgres + Redis without Docker — Django answers in under 3 s, the worker connects in about 3 s, readiness goes green with all three checks, the Vite app renders "Backend readiness: ok", the admin logs in headlessly and lists every Karni model, and `karni check`/`karni seed` exit 0 on a pristine scaffold. What is not in good shape is the front door: `docs/quickstart.md` cannot be followed as written — `karni test` fails for want of pytest (CI hides this by injecting it), and the served app returns 500 on login, docs and lists because the page never points `REDIS_URL` at a running Redis, so the "sign in and create an Event" finale is unreachable. Add `karni --version` not existing and `karni doctor` crashing in the quickstart's own directory layout, and a new user's first ten minutes contain four failures the framework's own tests do not catch. The Docker path remains entirely unverified on this machine.
