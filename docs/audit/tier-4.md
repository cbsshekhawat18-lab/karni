# Tier 4 audit — the quiet promises

*Repo `/Users/chandrabhanshekhawat/Documents/www/Karni`, branch `main`, commit `0873e51`. Audited 2026-10-19 against a scratch project made with `karni new audit4` (local PostgreSQL 17 `karni_audit_t4`, Redis db 8, no Docker, the repo's `.venv`). Report only: no tracked file was changed; everything below is observed output, kept under `docs/audit/evidence/tier-4/`. Verdicts: PASS / PARTIAL / FAIL / UNVERIFIED.*

How the scratch project was built (`evidence/tier-4/karni-new.log`, `scratch-project/`): `karni new audit4` → `karni make app events` → `Venue`, `Event(organizer, venue)`, `Booking(event, attendee, quantity)` each `--with viewset,test` → `karni add payments` → one `.env` edit for the local Postgres/Redis. Three deliberately broken viewsets were added for the audit and registered through the documented `KARNI_API_ROUTER` escape hatch (`scratch-project/config_api.py`): `SlowBookingViewSet` (`optimize = False`), `LeakyEventViewSet` (`filter_queryset_for_user` returns every row) and `CanVenueViewSet` (`Can(...)` predicate).

## Findings ranked by what they cost a real user

1. **The backend enforcement is switched off in every project `karni new` produces (and in `examples/eventhub`).** `karni_settings()` and the scaffold's `config/settings.py` never define `BASE_DIR`; `project_app_configs()` returns `[]` without it; every architecture rule, the duplication rule and the scaling check iterate that empty list. Observed: a project with a redundant serializer and an unpaginated `@action` gets `karni check: ok` (exit 0) and `9 passed, 1 skipped`; one settings line turns that into `karni check: FAILED` with both violations named and `2 failed`. The docs ("Every rule fails a build — nothing warns", `make check`, the CI step in `ci.yml:284`) describe a gate that is not there. Nothing warns that zero apps were scanned, `karni context` happily lists the app (it infers the root), and Karni's own tests monkeypatch discovery so the suite cannot notice. Cost: every promise in docs/enforcement.md's backend table is vacuous for a real user until they discover `BASE_DIR` on their own; the only backend things that actually fail a build today are the Django system checks (E101 and friends), which do not need discovery. (Evidence: `enforcement-base-dir.txt`, `enforcement-python.txt`.)
2. **Every error message and `karni explain` ends in a dead link.** `DOCS_BASE_URL` points at `https://cbsshekhawat18-lab.github.io/karni/`, which returns 404 for the root and for `errors/#<code>`. The messages themselves are good (code, the class/setting, the fix); the link that the docs call "the exact fix" leads nowhere. Cost: an agent or person that follows the URL loses the trust the message just earned. (`docs-url-curl.txt`.)
3. **Copying a `@karni/ui` component into a project is not detected as duplication.** `karni check` runs jscpd over `src/` only and never runs ESLint; a verbatim 617-line `ResourceTable` copy passes `karni check` untouched. ESLint (if the user runs it) rejects it for one raw `<table>`; a reasoned `eslint-disable` line makes the whole copy lint-clean. Two copies inside `src/` are caught. So the "reuse @karni/ui, never fork" argument rests on one JSX rule plus an honour-system comment; it is decorative against library-vs-project duplication. (`enforcement-eslint-*.txt`, `enforcement-jscpd-duplicate.txt`, `enforcement-python.txt` §A.)
4. **The scaling check does not exercise `?expand=`.** With discovery on, `SlowBookingViewSet` (`optimize = False`) passes the scaling check because the default serializer renders FKs as PKs; the 38-query N+1 only exists with `?expand=event.venue,event.organizer`, which the check never sends. The per-request budget catches it — but only in a test that hits the endpoint with that query string. The docs' "an N+1 at any level shows" is true for serializer-declared nesting, not for expansion. (`enforcement-base-dir.txt` §4, `pytest-nplus1.txt`.)
5. **The redundant-serializer rule is split between a warning and a rule that may not run.** W101 is a system-check *warning* (build passes); the build-failing `redundant-serializer` rule depends on finding #1. `karni rules --check` (K106) does flag the file, so an agent using the single-file check sees it and a CI running `karni check` does not. (`enforcement-python.txt` §B.)
6. **`queryset.update()` silently bypasses the audit stamps and the only mention is a source docstring about `updated_at`.** `updated_by`/`updated_at` do not move; docs/models.md "Audit fields" does not say so; the planned `karni check` rule (ADR 0002 P4) does not exist. Combined with #5b (no field history anywhere; the admin's history tab says "Changed Name." and nothing else), an app that needs "who changed what, from what, to what" has nothing today — which the ADR and docs/security.md state honestly. (`audit-trail.txt`.)
7. **An unimportable backend path is a raw `ModuleNotFoundError`.** `KARNI_ACCOUNTS_EMAIL_BACKEND` and `KARNI_SEARCH_PROVIDER` pointing at a module that does not exist produce Python's traceback, no code, no fix. Only a wrong *kind* of class gets E201. (`errors-five.txt` §4.)
8. **Local Celery on macOS fails before Karni's task runs.** `celery -A config worker` with the default pool (spawn on macOS) crashed in `celery/app/trace.py` on every task; the webhook pipeline's redelivery-recovers-unprocessed path behaved as documented, and `--pool=solo` works. Not a Karni bug, but `karni worker` and the module's "keep the worker service running" give no hint, and without Docker that is the first thing a Mac user hits. (`celery-worker.log`.)
9. **Explicit router registration order changes relation scoping.** Registering a second viewset for a model before `autodiscover()` makes it the viewset relation fields validate against ("first registered wins"); the generated `assert_crud` then fails with `Invalid pk`. Documented in `routers.py`, invisible from the error. (`pytest-nplus1-and-oneliners.txt`, first run.)
