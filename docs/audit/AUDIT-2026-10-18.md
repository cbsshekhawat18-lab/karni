## 1. Data leaks (Tier 3)

**One confirmed cross-tenant data leak, in the Django admin. A branch manager
who is `is_staff` and whose group holds Django's ordinary `view_employee` /
`change_employee` model permissions reads and edits every branch's rows: the
changelist returned all 9 employees including the other branch's names and a
9000.00 salary; the change form of another branch's row showed its salary and
the API-write-only `secret_note` value; a POST renamed that row and the change
persisted (confirmed through the API as the other branch's manager); `?q=`,
the branch list filter and the autocomplete endpoint all surfaced the other
branch's rows. `karni.admin` applies no row scope at all: the admin base
classes lift only soft-delete and never apply `access.read` or
`rows_for(user, model, "view")`. This is the ADR 0002 P2 admin half,
documented as planned and unbuilt, and it leaks today because the admin
surface exists while its scope does not. The REST API enforced isolation
perfectly under the same probes, so an operator will assume both surfaces
share a policy. Until P2-admin ships, the only safe posture is superusers
only in the admin, and nothing but an ADR says so.** Evidence:
[tier-3.md § LEAKS](tier-3.md#leaks),
[evidence/tier-3/admin2.log](evidence/tier-3/admin2.log).

No other route leaked another tenant's row. Three weaknesses are leak-adjacent
but are not row leaks:

- **Hidden fields are an ordering (and, if listed, search) oracle.**
  `ordering_fields = "__all__"` validates against model fields, so
  `?ordering=secret_note` reorders the list by a value the serializer never
  returns; `?ordering=created_by__password` and `deleted_at` are accepted and
  executed. Only rows the caller may already read are reordered. The shipped
  test `test_write_only_fields_are_not_orderable` passes by coincidence: its
  fixture data makes the hidden-field order equal the default order. A
  counter-test on Karni's own fixtures shows `?ordering=internal_note`
  reordering `EventViewSet`. Evidence: [tier-3.md § Counter-test](tier-3.md#counter-test-shipped-test-is-coincidentally-green),
  [evidence/tier-3/scope.log](evidence/tier-3/scope.log) #26–#32,
  [evidence/tier-3/search2.log](evidence/tier-3/search2.log) #19.
- **Relation-id disclosure.** The primary key of an unreadable row is returned
  when its readable owning row is serialized unexpanded (expanded, it renders
  `null`). An id oracle across the boundary, no field data.
  [evidence/tier-3/scope.log](evidence/tier-3/scope.log) #96–#97.
- **Password spraying when Django is exposed without the shipped proxy.** The
  per-IP login throttle trusts `X-Forwarded-For` (`NUM_PROXIES=1`); rotating
  the header across distinct accounts produced no 429 in 14 attempts. The
  per-account throttle still bounds attacks on one mailbox. A deployment
  caveat, not a code flaw. [evidence/tier-3/auth2.log](evidence/tier-3/auth2.log) #38–#51.

## 3. Everything FAIL or PARTIAL, ranked by what it costs a real user

1. **Admin has no row scope (Tier 3, FAIL, leak).** Any non-superuser role
   given ordinary Django model permissions reads and writes every tenant's
   rows in the admin, including fields the API hides. Highest blast radius:
   invisible from the API, and the way every Django shop admits a role.
   [tier-3.md](tier-3.md#leaks) · [admin2.log](evidence/tier-3/admin2.log)
2. **`karni check` and the architecture suite enforce nothing in any
   `karni new` project, nor in examples/eventhub (Tiers 2 f, 4 1c/2c/2e,

## 4. Launch recommendation

**NOT YET.**

What blocks a launch (each observed, not inferred):

1. The admin row-scope leak (item 1). Either ship P2-admin, or before any
   announcement make "superusers only in the admin" a loud, checked rule
   rather than a line in an ADR.
2. Enforcement that checks zero files (item 2). The product's central claim
   is that the rules fail a build; in every project Karni generates they do
   not. The auditors' experiment shows a single `BASE_DIR` definition makes
   it real; a test that exercises discovery against a real scaffold is also
   missing.
3. The quickstart (item 3). A first-time user hits `karni test` failing,
   then a wall of 500s on their first click. The page needs a running Redis
   and a `REDIS_URL` line, and pytest in its install line, before anyone is
   sent to it.
4. Search 500 on the default PostgreSQL stack (item 4).
5. Launch mechanics: the packages are unpublished and the docs site is not
   deployed, so quickstart line one and every error link fail today (items
   3 and 5). These are already on docs/launch-checklist.md; they stay blocking
   until done.

Should be fixed before announcing, not strictly blocking: the unsubmittable
generated form (6), `karni doctor` (7), MCP `context` (8), the ordering
oracle and its coincidental test (9), the missing worker hint and macOS pool
note (13), `karni --version` (14), the mypy error (15), stale README counts
(23).

Caveats that can stand with honest wording: the Docker path is unverified
here; the `X-Forwarded-For` posture needs one sentence in docs/security.md;
P3 field visibility, P4 change history and P6 import/export are absent and
the docs already say so; the UI duplication story should be described as the
ESLint rule it is.

What held up, observed end to end: packaging and clean install; the local
stack boots in about 30 seconds of commands; the data layer, generated API,
zero-code admin, optimiser, query budgets, isolation test, webhook pipeline,
audit stamps, roles-as-data helpers, adapters, `karni context` and the
upgrade codemods; and the API access model, which refused every one of
roughly fifty cross-tenant and privilege-escalation probes.
